## Overview

This plan implements the **Recurrent Toroidal Cortical Columns (RTCC)** architecture and all ablation variants needed for a research paper. The core idea: reshape model embedding dimensions into a 2D toroidal grid, slide N×N expert patches over it with a 1-cell overlap border, and stack these sheets via recurrent looping to form cortical columns. See architecture description below.

The plan has five major deliverables:
1. Shared infrastructure (data pipeline, training loop, eval harness, database)
2. Five architecture implementations
3. Ablation sweep configurations
4. Analysis and visualization scripts
5. Paper figure generation

### Shared Parameters (all architectures unless noted)

```yaml
vocab_size: 50000

n_heads: 12               # query heads (768 / 64 = 12)
head_dim: 64              # power of 2, gold standard ✓
mla_latent_dim: 192       # KV compression latent dim (~model_dim / 4)
mla_rope_dim: 32          # decoupled RoPE portion of query/key
prelude_layers: 4
coda_layers: 1
max_loop_iters: 8         # validated optimum from CART (Model_Paper_1) ablations
warmup_steps: 2000
lr_max: 3.0e-4
lr_min: 3.0e-5
weight_decay: 0.1
grad_clip: 1.0
batch_size: 4
grad_accum_steps: 8
seed: 42
```

**Attention: MLA (Multi-head Latent Attention) — DeepSeek-V2 (Dai et al., 2024)**

MLA compresses K and V into a low-rank latent vector rather than caching full K/V heads:
```
Input → W_DKV → c_KV  [batch, seq, mla_latent_dim]   ← what gets cached
c_KV  → W_UK  → K     [batch, seq, n_heads, head_dim]
c_KV  → W_UV  → V     [batch, seq, n_heads, head_dim]
```
Decoupled RoPE is applied to a separate `mla_rope_dim`-dimensional portion of Q and K, not to the full head. This is critical — implement exactly as in DeepSeek-V2 or the attention behavior will be wrong.

**MLA head config by location:**

| Location | Type | Heads | Notes |
|---|---|---|---|
| Prelude (4 blocks) | MLA | 16-head | Runs once, heavier |
| Recurrent core (6 blocks) | MLA | 12-head | Shared weights, looped R times |
| Coda (1 block) | MLA | 8-head | Lightweight |

**KV cache note:** MLA caches `c_KV` (latent dim=192) not full K/V (would be n_heads × head_dim = 768). This is the primary memory advantage of MLA over GQA at inference time.

**Implementation:** `shared/components/attention.py` must implement MLA faithfully. Reference the DeepSeek-V2 paper (arXiv 2405.04434) and the kyegomez/OpenMythos codebase which this project is based on. Do not implement GQA — the KV cache structure is fundamentally different.

**Grid at 768-dim:** 768 = 32×24 (rectangular toroidal grid, 32 rows × 24 cols)

**Why rectangular is fine:** A torus does not need to be square. The cortical sheet analogy holds on a rectangular torus. The only requirement is ≥3 experts per axis, which all paper configs satisfy. The non-square shape is described accurately in the paper — no apology needed.

**Head dim note:** head_dim=64 with n_heads=12 is clean, standard, and uses flash attention's optimal kernel path. This is the primary reason for choosing 768 over 784. MLA's latent compression means the KV cache footprint is mla_latent_dim=192 per token per layer, not n_heads×head_dim=768 — a 4× KV cache reduction vs standard attention.

### Architecture 03: SliceMoE Flat (Tier 1 Baseline)

```

No overlap — adjacent slices share 0 dims
Experts see a 64-dim slice of the full 768-dim embedding
Position-fixed — each expert owns its slice, no routing needed
```

This is the cleanest non-overlapping partition at 768-dim. 12 experts × 64 dims tiles exactly. The 64-dim per expert matches the private core size of the primary RTCC config, making the comparison controlled.

**Implementation note:** The SliceMoE paper (arXiv 2510.04286) is the prior art here. Key difference from RTCC: no overlap between slices, no toroidal boundary. Position-fixed experts are retained to isolate the overlap contribution specifically.

**Purpose:** Validates that the overlap mechanism (not just dimensional partitioning) is what makes RTCC work. Expected to outperform standard MoE but underperform RTCC.

#### Toroidal MoE Implementation

This is the core of the paper. Implement with extreme care.

**Forward pass:**

```python
def forward(self, x):
    # x: [batch, seq_len, model_dim]
    B, S, D = x.shape

    # 1. Reshape embedding to 2D grid
    x_grid = x.view(B, S, self.grid_rows, self.grid_cols)
    # x_grid: [batch, seq_len, 32, 24]  (768 = 32×24)

    # 2. Toroidal padding (circular on both axes)
    # overlap = patch_size - stride
    # Primary config: patch=10, stride=8, overlap=2
    overlap = self.patch_size - self.stride
    x_padded = self._toroidal_pad(x_grid, overlap)
    # x_padded: [batch, seq_len, 32+2*overlap, 24+2*overlap]

    # 3. Extract patches via unfold
    # Unfold along row axis
    x_unf = x_padded.unfold(2, self.patch_size, self.stride)
    # Unfold along col axis
    x_unf = x_unf.unfold(3, self.patch_size, self.stride)
    # x_unf: [batch, seq_len, n_expert_rows, n_expert_cols, patch_h, patch_w]
    n_er, n_ec = x_unf.shape[2], x_unf.shape[3]
    n_experts = n_er * n_ec

    # 4. Flatten patches for expert processing
    x_patches = x_unf.reshape(B * S * n_experts, self.patch_size * self.patch_size)
    # x_patches: [batch*seq*n_experts, patch_dims]

    # 5. Apply experts (ALL experts always active — position-fixed, no routing)
    # Each expert is a small MLP: patch_dims → hidden → patch_dims
    expert_idx = torch.arange(n_experts, device=x.device)
    expert_idx = expert_idx.unsqueeze(0).expand(B * S, -1).reshape(-1)
    x_out = self.expert_mlps(x_patches, expert_idx)
    # x_out: [batch*seq*n_experts, patch_dims]

    # 6. Reshape back
    x_out = x_out.reshape(B, S, n_er, n_ec, self.patch_size, self.patch_size)

    # 7. Overlap-add fold (accumulate shared dims)
    output = self._overlap_add_fold(x_out, B, S)
    # output: [batch, seq_len, grid_rows, grid_cols]

    # 8. Reshape back to flat embedding
    return output.view(B, S, D)

def _toroidal_pad(self, x, overlap):
    # x: [B, S, H, W]
    # Circular pad on both spatial dims
    x = torch.cat([x[:, :, -overlap:, :], x, x[:, :, :overlap, :]], dim=2)
    x = torch.cat([x[:, :, :, -overlap:], x, x[:, :, :, :overlap]], dim=3)
    return x

def _overlap_add_fold(self, x_out, B, S):
    # Inverse of unfold with overlap-add accumulation
    # This is the key mechanism: shared dims receive gradient from multiple experts
    H, W = self.grid_rows, self.grid_cols
    output = torch.zeros(B, S, H + 2*self.overlap, W + 2*self.overlap,
                         device=x_out.device, dtype=x_out.dtype)
    n_er, n_ec = H // self.stride, W // self.stride
    for i in range(n_er):
        for j in range(n_ec):
            r_start = i * self.stride
            c_start = j * self.stride
            output[:, :, r_start:r_start+self.patch_size,
                         c_start:c_start+self.patch_size] += x_out[:, :, i, j]
    # Remove padding (trim to original grid size)
    output = output[:, :, self.overlap:-self.overlap, self.overlap:-self.overlap]
    return output
```

**IMPORTANT implementation notes:**
- The overlap-add fold loop is correct for clarity but should be replaced with `torch.nn.functional.fold` for GPU efficiency after validation
- All experts are ALWAYS active (no routing) — this is position-fixed, not top-k
- The double-loop in fold will be slow; optimize after correctness is verified
- Expert MLPs use SwiGLU: `patch_dims → hidden_dim → patch_dims` with 3 weight matrices
- Expert weights are stored as a batched parameter: `nn.Parameter(torch.zeros(n_experts, patch_dims, hidden_dim))`

**Expert MLP spec (RTCC full, 768-dim, 10×10 patch, stride 8, 2-cell overlap):**
```
grid:          32×24 = 768 dims
patch:         10×10 = 100 dims per expert
stride:        8
overlap:       2 cells (= 10 - 8)
n_expert_rows: 32÷8 = 4
n_expert_cols: 24÷8 = 3
n_experts:     4×3 = 12 per loop  (≥3 per axis ✓)
private_core:  (10-4)×(10-4) = 6×6 = 36 dims
privacy_pct:   36/100 = 36%  ← NOTE: see privacy sweep for higher privacy configs
hidden_dim:    256
params/expert: 100×256×3 = 76,800
total MoE/loop: 12 × 76,800 = 921,600 (~0.9M)
total MoE × 6 loops: ~5.5M
```

**Primary RTCC config note:** The 10×10 stride-8 config (2-cell overlap, 36% privacy) is the architecturally "full" RTCC used for Tier 1 baseline comparison. The privacy sweep explores other configs up to 64% privacy. The primary config was chosen because it sits in the middle of the sweep range, making it the most representative single config for the Tier 1 comparison.

**Privacy sweep — all configs verified ≥3 experts per axis:**

Overlap formula: `overlap = patch_size - stride`
Private core: `private_side = patch_size - 2×overlap`, `private_dims = private_side²`
Privacy%: `private_dims / patch_size²`

| Config | Patch | Stride | Overlap | Experts (R×C) | Min axis | Private side | Private dims | Privacy% |
|--------|-------|--------|---------|---------------|----------|-------------|-------------|---------|
| sweep_11 | 3×3 | 2 | 1 | 16×12=192 | 12 ✓ | 1 | 1 | 11% |
| sweep_36 | 5×5 | 4 | 1 | 8×6=48 | 6 ✓ | 3 | 9 | 36% |
| sweep_44 | 6×6 | 4 | 2 | 8×6=48 | 6 ✓ | 2 | 4 | 11% |
| sweep_60 | 9×9 | 8 | 1 | 4×3=12 | 3 ✓ | 7 | 49 | 60% |
| sweep_64 | 10×10 | 8 | 2 | 4×3=12 | 3 ✓ | 6 | 36 | 36% |

**Important:** The controlled pairs (sweep_36 vs sweep_44 at 48 experts, sweep_60 vs sweep_64 at 12 experts) isolate overlap width at constant expert count. Privacy% values may not be as spread as originally hoped — the paper frames these as "overlap width ablation" pairs rather than "privacy sweep" per se. The sweep_11 and sweep_60 endpoints provide the range anchors.

**Claude Code must compute privacy% from first principles in RTCCConfig:**
```python
self.overlap = self.patch_size - self.stride
self.private_side = self.patch_size - 2 * self.overlap
self.private_dims = self.private_side ** 2
self.privacy_pct = self.private_dims / (self.patch_size ** 2)
# Guards
assert self.private_side >= 1, "No private dims — reduce overlap or increase patch"
assert self.grid_rows % self.stride == 0, "Stride does not tile row axis"
assert self.grid_cols % self.stride == 0, "Stride does not tile col axis"
assert self.grid_rows // self.stride >= 3, "Too few experts on row axis (need ≥3)"
assert self.grid_cols // self.stride >= 3, "Too few experts on col axis (need ≥3)"
```

## DB Logging

Every training step writes to the `steps` table. The `db_logger.py` module handles this with a write-ahead log (WAL) mode for performance:

```python
class DBLogger:
    def __init__(self, db_path, run_id):
        self.conn = sqlite3.connect(db_path)
        self.conn.execute("PRAGMA journal_mode=WAL")  # non-blocking writes
        self.run_id = run_id
        self.buffer = []
        self.flush_every = 100  # batch writes every 100 steps

    def log_step(self, step, loss, aux_loss, grad_norm, lr,
                 n_loops, seq_len, tokens_seen, phase, sec_per_step):
        self.buffer.append((self.run_id, step, loss, aux_loss, grad_norm,
                            lr, n_loops, seq_len, tokens_seen, phase, sec_per_step))
        if len(self.buffer) >= self.flush_every:
            self.flush()

    def flush(self):
        self.conn.executemany("""
            INSERT OR IGNORE INTO steps
            (run_id, step, loss, aux_loss, grad_norm, lr, n_loops,
             seq_len, tokens_seen, phase, sec_per_step)
            VALUES (?,?,?,?,?,?,?,?,?,?,?)
        """, self.buffer)
        self.conn.commit()
        self.buffer.clear()
```

**Run registration:** Before training starts, `launch_run.py` inserts a row into `runs` with all hyperparameters and sets `status='running'`. On completion, updates `status='complete'` and `completed_at`. On crash/interrupt, a signal handler sets `status='interrupted'`.
